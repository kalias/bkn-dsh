# bkn-dsh / DSH 0.1.6-alpha.2 兼容分支审核报告

日期：2026-09-19  
审核方式：只读静态审查、Git 历史与现有构建产物检查；未切换分支、未 reset、未运行会改写产物的 build/test。  
审核范围：

- `bkn-dsh`：`feat/dsh-0.1.6-alpha.2-compat`
- `deepseek-harness`：
  - `fix/mcp-credential-headers`
  - `fix/typert-external-protocol`

## 1. 结论

当前实现已经在构建机上完成实际端到端验证，但**尚不具备跨机器发布条件**。正式 Release、市场投稿或上游合并前，必须优先解决：

1. CI generator override 必然失败；
2. Runtime 压缩包包含构建机绝对符号链接和绝对 file 依赖，不可移植；
3. Runtime 构建会在 compat manifest 之外修改 pinned DSH 源码并非冻结更新 lockfile，无法重复构建；
4. pnpm 和 Node.js 版本契约互相矛盾。

## 3. 发布阻断项

### BLOCKER-1：CI generator override 与实际 workspace 不一致

证据：

- `pnpm-workspace.yaml:8`：

  ```yaml
  '@deepseek-ai/dsh-typert-generator': link:../deepseek-harness/packages/typert/generator
  ```

- `scripts/configure-pinned-dsh-generator.mjs:5` 只识别：

  ```js
  link:../../../../../DSH/deepseek-harness/packages/typert/generator
  ```

- `.github/workflows/compatible-runtime.yml:40` 会直接调用该脚本。

结果：CI 会在安装前抛出 `Expected exactly one local DSH generator override`。

现有 `tests/configure-pinned-dsh-generator.test.mjs:6` 使用旧路径构造 fixture，没有测试真实 `pnpm-workspace.yaml`，因此无法发现漂移。

验收标准：

- 配置脚本不依赖某台开发机的固定路径；
- 对实际 workspace 文件执行配置成功；
- 重复配置或未知 override 形态仍保持失败即拒绝；
- CI 中该步骤通过。

### BLOCKER-2：Runtime 产物不可移植

现有压缩包：

```text
release/artifacts/openbkn-dsh-runtime-0.1.6-alpha.2-openbkn.1-darwin-arm64.tar.gz
```

包含构建机绝对符号链接，例如：

```text
@deepseek-ai/cosmokit
  -> /Users/kalias/Documents/project/app/openBKN/deepseek-harness/vendor/cosmokit

@deepseek-ai/schemastery
  -> /Users/kalias/Documents/project/app/openBKN/deepseek-harness/vendor/schemastery

runtime/node_modules/.bin/cordis
  -> /Users/kalias/Documents/project/app/openBKN/bkn-dsh/release/runtime/...
```

profile 模板也包含绝对依赖：

```json
"@openbkn/dsh-business-context":
  "file:/Users/kalias/Documents/project/app/openBKN/bkn-dsh/release/plugin/openbkn-dsh-business-context-0.1.4.tgz"
```

相关代码：

- `runtime/prepare-runtime-profile.mjs`
- `runtime/assemble-compatible-runtime-bundle.mjs:71-74`
- `runtime/bootstrap-openbkn-plugin.mjs`

现有 E2E 是在构建机上执行，绝对链接仍能命中原目录，因此没有验证真正的跨机器可用性。

验收标准：

- tar/zip 中不存在绝对符号链接；
- tar/zip 文本文件中不存在构建机 home 路径；
- profile 中不存在构建期 `file:/absolute/path`；
- 将压缩包复制到独立临时目录、移除/隐藏源码树后，`bin/dsh --version` 和 `bin/dsh web --no-open` 仍可启动；
- 增加自动化 portability 测试。

### BLOCKER-3：构建过程不可重复且修改 manifest 外文件

`runtime/prepare-compatible-runtime.mjs:43-53` 会：

1. 直接删除 pinned DSH `pnpm-workspace.yaml` 中的 `@electron/osx-sign` patch 注册；
2. 执行 `pnpm install --no-frozen-lockfile`；
3. 使 DSH 工作树在 compat patch 之外产生变化。

CI 对 bkn-dsh 本身也使用 `.github/workflows/compatible-runtime.yml:43` 的 `--no-frozen-lockfile`。

影响：

- lockfile 解析结果取决于时间、registry 与 pnpm 版本；
- compat manifest 不再完整描述构建源码；
- 构建后无法继续满足“精确 commit + 干净工作树”；
- 当前 DSH `pnpm-lock.yaml` 大范围漂移即为风险表现之一。

验收标准：

- release 构建必须使用 frozen lockfile；
- 所有必需源码改动均由受摘要保护的 compat patch 描述；
- build 前后除明确输出目录外，pinned DSH 工作树不产生额外 diff；
- 相同源码/工具版本重复构建具有一致依赖闭包。

## 4. 高风险问题

### HIGH-1：pnpm 主版本不一致

- DSH 0.1.6-alpha.2 根 `package.json`：`pnpm@11.7.0`
- 本地：pnpm 11.21.0
- CI：`.github/workflows/compatible-runtime.yml:32` 固定 pnpm 10

这会改变 lockfile 与 patchedDependencies 行为，也是本地/CI 偏差的主要来源。

建议：CI 与开发基线统一到 DSH 声明的 pnpm 11.7.0；若必须偏离，需明确记录并加入 lockfile 兼容测试。

### HIGH-2：Node.js 要求互相矛盾

- `README.zh.md:36`、`README.md:36`、`runtime/openbkn-dsh-runtime.manifest.json:6`：Node.js >=20
- `packages/openbkn-business-context/package.json:21-22`：`^22.19.0 || >=24.0.0`
- DSH 0.1.6-alpha.2 根 `package.json`：`^22.19.0 || >=24.0.0`

Node 20/21 用户会被文档允许启动不受支持的 Runtime。

建议：Runtime manifest、README、启动前检查和插件 engines 使用同一版本约束。

### HIGH-3：第三方补丁声明不一致

DSH 提交 `839a201536` 从 `THIRD_PARTY_NOTICES.md` 删除了 `@electron/osx-sign@1.3.3` patch 说明，但该提交中：

- patch 文件仍存在；
- `pnpm-workspace.yaml` 仍注册 patch；
- lockfile 仍记录 patch。

当前未提交 workspace 改动又删除 patch 注册，但 patch 文件仍在。需要明确该 patch 是否仍属于发布闭包，并保证 patch 文件、workspace、lockfile、NOTICE 四者一致。

## 5. 中风险问题

### MEDIUM-1：credentialHeaders 补丁未被插件消费

compat 0001 为 DSH MCP client 增加 credential-backed headers，但插件仍在：

- `packages/openbkn-business-context/src/openbkn-mcp-manager.ts:42-53`

主动解析 Token 并传入：

```ts
headers: { Authorization: `Bearer ${token}` }
```

因此当前插件并未走 `credentialHeaders` 路径。后果：

- compat fork 面积大于实际运行需要；
- MCP 自动 reconnect 会继续使用创建 transport 时的 Token；
- Token 轮换依赖外层显式 `refresh()`；
- 注释仍写 DSH 0.1.2，与当前 0.1.6 分支不符。

需要明确二选一：

1. 插件改用 credential reference，保留 compat 0001；
2. 若现有内存注入已满足安全/轮换需求，则删除无用补丁并缩小 fork 面。

### MEDIUM-2：`permission_denied` 被过度映射为 License 问题

`packages/openbkn-business-context/src/platform-reader.ts:115-122` 将所有 HTTP 401/403 且 `error.code=permission_denied` 的响应映射为 `LICENSE_REQUIRED`。

同一错误码也可能表示：

- Token scope 不足；
- 用户无知识网络权限；
- business domain 配置错误；
- 认证信息失效。

建议只在 provenance/observability 路由或平台返回明确 license feature gate 时映射为 License 提示。

### MEDIUM-3：关键 DSH 改动缺少自动化行为测试

DSH 三个分支主要改动：

- `fix/mcp-credential-headers`
- `fix/typert-external-protocol`
- `feat/ignorable-session-events-write-side`

不足：

- MCP credential header 没有覆盖：缺失 credential、prefix、literal header 覆盖、reconnect 后轮换；
- session write-side 没有直接测试 append 未知 ignorable event + 保存/重载；
- Typert 分支建立在 MCP 分支之上，如计划独立提交上游，会夹带前序提交。

人工 E2E 证据有效，但不能替代分支级回归测试。

### MEDIUM-4：Release workflow 缺少发布门禁

当前 tag workflow 没有运行：

- 插件完整测试；
- typecheck；
- package bundle 检查；
- compat 测试；
- Runtime portability 扫描；
- 绝对路径/绝对 symlink 检查。

需要在 publish job 前加入统一 gate。

### MEDIUM-5：静态检查返回类型告警

自动检查报告：

- `src/dsh-session-binding.ts:25`
- `src/dsh-session-provenance.ts:24`

接口方法 `append(...): unknown` 触发 `no-unknown-returns`。这在能力面声明中可能是刻意表达“调用方不依赖返回值”，但应明确处理：

- 若真实 DSH API 返回值可表示，使用具体类型；
- 若调用方永远忽略返回值，可评估使用 `void`；
- 若必须保持 `unknown`，添加精确的局部说明或规则豁免，避免长期 blocker。

## 8. 建议修复顺序

1. 修复 generator override 与真实 workspace/CI 的契约；
2. 修复 Runtime/profile 中绝对路径与绝对 symlink；
3. 统一 pnpm 11.7.0，恢复 frozen lock；
4. 将本地 `osx-sign` workaround 转为显式、可验证的 compat 策略；
5. 统一 Node.js 版本声明；
6. 决定并统一 credentialHeaders 使用策略；
7. 收窄 License 错误分类；
8. 补齐单元测试、portability 测试和 Release gate；
9. 最后重新构建干净 Runtime，在隔离路径做端到端验证。
