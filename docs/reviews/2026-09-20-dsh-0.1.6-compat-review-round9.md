## 4. 本轮新发现（源码层）

### N1（P1，合入前处理）MCP 端点缺少 scheme/host 围栏，Bearer token 可被配置发往任意主机

**事实链**：

1. `config.ts`：`mcpUrl: Schema.string()`——自由字符串，无校验。
2. `openbkn-mcp-manager.ts:71` `resolveMcpUrl()`：`if (config.mcpUrl?.trim()) return new URL(config.mcpUrl).toString()`——只做 URL 语法解析，不校验 scheme，也不校验 host 是否属于 `baseUrl` 所在平台。
3. 同文件 `start()`：把 `Authorization: Bearer <token>` 直接挂到该 URL 的 streamable-http 客户端上。

**对照**：控制面读取器 `platform-reader.ts:206 fixedUrl()` 有围栏——非 loopback 必须 https，否则 `PLATFORM_MISMATCH`；`AuthCoordinator.status()` 还有 baseUrl 平台围栏。**同一个 token，两条出站路径的保护强度不一致**，而 MCP 这条恰恰是每回合都会重挂的主路径。

**影响**：`mcpUrl` 写成 `http://…` 时，token 以明文过网；写成任意外部主机时，token 直接发给该主机。这不是远程攻击者可触发的路径（需要改 DSH 插件配置），但配置可能随 profile 分发/同步，且与 README、compat README 声明的「token 只进 DSH credentials、只发往配置的平台」边界不符。fail-closed 项目里这属于该堵的口子。

**建议修复**：把 `fixedUrl` 的判定抽成共享函数并用于 `resolveMcpUrl`——非 loopback 强制 https（`allowInsecureTls` 下才允许 http）；默认再加一条 host 围栏：`new URL(mcpUrl).origin` 必须等于 `new URL(baseUrl).origin`，需要跨主机时要求显式开关。
**验收**：新增单测——`http://` 非 loopback 被拒、跨 origin 被拒、loopback http 放行、默认路由不受影响；`pnpm --filter @openbkn/dsh-business-context test` 全绿。

### N2（P2）响应体先全量缓冲再判上限，`content-length` 缺失即绕过 8 MB 门槛

`platform-reader.ts:133-145`：先看 `content-length`，缺失就跳过检查；随后 `await response.text()` **把整个响应读进内存**，之后才按 8 MB 判定。平台若不带该头（chunked）或行为异常，Host 进程可被撑爆——DSH Host 是本地长驻进程，OOM 即整个会话中断。
**建议**：改用 `response.body` 逐块读，累计超过 `MAX_PLATFORM_RESPONSE_BYTES` 立即 abort 并抛 `OUTPUT_OVERFLOW`。
**验收**：单测用一个不带 content-length、超过上限的流式 fixture，断言抛 `OUTPUT_OVERFLOW` 且未把全部字节读完。

### N3（P2）控制面请求跟随重定向

`request()` 未设 `redirect`，即默认 `follow`。undici 在跨 origin 重定向时会剥掉 `authorization`，所以**没有可证实的 token 泄漏**；但固定路由的控制面读取器跟随重定向本身没有收益，还会让 https→http 降级与端点漂移变得静默。
**建议**：`redirect: 'error'`，3xx 直接落到 `PLATFORM_UNAVAILABLE`。
**验收**：单测断言 302 fixture 不被跟随。

### N4（P3）`allowInsecureTls` 名实不符

该开关只放宽「允许 http scheme」，完全不影响 TLS 证书校验（代码里没有任何 agent/证书配置）。用户为「接受自签证书」打开它不会生效，只会拿到一个笼统的 `PLATFORM_UNAVAILABLE`；而打开后 token 可明文发往任意非 loopback 主机（与 N1 叠加）。
**建议**：改名 `allowPlaintextHttp`（保留旧键兼容或在 CHANGELOG 注明），config 注释写清「不影响证书校验」。

### N5（P3）`businessDomain` 未校验即作为请求头值

自由字符串 `.trim()` 后直接进 `x-business-domain`。含非法字符时 undici 抛错，被外层 catch 归为 `PLATFORM_UNAVAILABLE`——fail-closed 但报错误导。
**建议**：`Schema.string().pattern(/^[A-Za-z0-9_-]{1,64}$/)`，或在读取器里做一次同样的校验并抛 `PLATFORM_MISMATCH`。

### N6（P3）`ensure()`/`refresh()` 存在窄竞态

`refresh()` 先 `await this.starting`、再 dispose、再 `ensure()`；而 `ensure()` 的首行是「工具已注册就直接返回」。若 dispose 期间有并发 `ensure()`，旧 fiber 的工具可能仍在注册表里，导致该次 ensure 早退、拿到即将被销毁的客户端。实际触发窗口很窄（同回合内并发），但每回合重挂的设计下并非不可能。
**建议**：refresh 期间置一个 `reloading` 标志，`ensure()` 命中标志时等待重挂完成再判断。

### N7（P3）workflow 冒烟注释与事实相反

`compatible-runtime.yml` 冒烟步骤注释写「the guard/bootstrap paths stay unexercised-but-honest」，但 `dsh.cmd` 的结构是：**守卫行先无条件执行**，`--version` 只跳过 bootstrap（`goto run`）。第八轮回应自己也写「Node 守卫在每次调用时先执行——比直驱 bin.js 覆盖更多」，两处矛盾。
**建议**：注释改为「守卫的放行路径每次都执行；跳过的是 bootstrap；守卫的拒绝路径仍未在原生 Windows 验证」。

### N8（P3）win32 冒烟未隔离 `OPENBKN_DSH_HOME`

mac 分支用 `mktemp -d` 隔离，win32 分支没有。当前因 `--version` 走 `goto run` 不触发 bootstrap 而无副作用，但这依赖启动器内部结构；一旦快捷路径调整，CI 就会去写 runner 的 `%LOCALAPPDATA%`。
**建议**：win32 分支也传入临时目录，保持两分支对称。

### R1（P3，round8 F3 残留）workflow 常量仍是字面量

`PLUGIN_ARTIFACT: …-0.1.4.tgz` 与 `BUNDLE_NAME: …-openbkn.1` 是 manifest / `package.json` 的副本。好处是版本漂移现在会**吵闹失败**（找不到文件即红），不会静默；但真相源仍有两处。可选改为从 manifest 与 package.json 推导。

### R2（P3，round8 F6 残留）绿点仍落在 HEAD-1

run#10 基线 `1b8d8a3`，HEAD `952d404` 为纯文档提交。建议回应里固定写明「绿点基线 = `1b8d8a3`，HEAD 与之仅差文档」，或在合入前再 dispatch 一次。

## 5. 源码层已核可的部分（本轮确认无问题，供后续少走重复路）

- `openbkn-cli-subprocess.ts`：三条命令白名单（`auth status --json` / `auth token` / `auth login <配置的 baseUrl>`），argv 数组直传、无 shell、输出 64 KB 上限且截断即抛错。命令注入面为零。
- `auth.ts`：token 做长度与换行校验；错误只带 stderr 摘要，不带 stdout（token 在 stdout）；平台围栏为字符串精确比较，不一致返回 `platform-mismatch`（fail-closed 方向）。
- `platform-reader.ts`：错误类型只带错误码与固定文案，不含响应体；403 分类严格限定在 `licenseGated` 路由且要求 `error.code === 'permission_denied'`；投影函数对字段做白名单 + 512 字符截断 + 数量收敛；`interactionId` 经 `encodeURIComponent`。
- `business-context-service.ts`：两处 `logger.warn` 只打印归一化的失败码（`safeRunnerFailureCode` / `safeCapabilityProfileFailureCode`），不打印 token、URL 或响应体；token 只在 `readToken → credentials.set → resolve` 闭环内流动，不进 Remote 返回值。
- 溯源双读用 `Promise.allSettled`，单边失败不掩盖另一边的安全事实；只有双失败才走 License 判定。
