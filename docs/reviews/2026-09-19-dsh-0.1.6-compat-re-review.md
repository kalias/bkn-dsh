## 3. 发现与修复验收

### R1 [P1] CI 在构建 generator 前运行插件测试

**位置**：`.github/workflows/compatible-runtime.yml:48–55`；`packages/openbkn-business-context/tsdown.config.ts:2`。

当前顺序：应用 compat → verify → revert → 插件 test → 构建兼容 DSH。

插件 test 包含构建，并引用链接到 DSH 源码树的 `@deepseek-ai/dsh-typert-generator/tsdown`。该包 exports 指向 `lib/`，干净 tag checkout 不含这些构建文件。测试执行时既未构建 generator，又已撤销补丁；本地残留的 lib 会掩盖问题。

**建议**：先完成受控的 apply/verify/revert 闭环，再重新应用补丁并安装、构建 DSH/generator，之后运行插件构建和测试。

**验收**：在没有历史 lib/node_modules 的干净工作区执行与 CI 相同的流程，generator 可解析且外部协议契约测试通过；不依赖本机构建缓存。

### R2 [P1] 可移植性检查位于产物生成之前

**位置**：`.github/workflows/compatible-runtime.yml:62–65`；`scripts/check-runtime-portability.mjs:23–27`；`scripts/package-compatible-runtime.mjs:51–57`。

`Check runtime portability` 先于 `Package runtime archive`。被检查的目录由后者调用 assemble 时创建；干净 runner 上目录不存在，检查必然失败。

**建议**：采用 assemble → 检查 → archive → 上传，或打包后检查并阻止失败产物上传。避免检查上一轮残留产物。

**验收**：输出目录最初不存在也能走通流程；人为植入违规路径时 publish/upload 被阻止。

### R3 [P1] 可移植性门禁漏检，产物仍含构建路径与无效 file 引用

**位置**：`runtime/bundle-portability.mjs:21–24、80–89`；`runtime/assemble-compatible-runtime-bundle.mjs:113`。

实际产物：

```text
release/artifacts/openbkn-dsh-runtime-0.1.6-alpha.2-openbkn.1-darwin-arm64.tar.gz
```

官方检查返回成功，但独立扫描发现下列 7 个文件仍含 `/Users/kalias`：

```text
profile-template/web/node_modules/.modules.yaml
profile-template/web/node_modules/.pnpm-workspace-state-v1.json
profile-template/web/home/profiles/web/node_modules/.modules.yaml
profile-template/web/home/profiles/web/node_modules/.pnpm-workspace-state-v1.json
runtime/node_modules/.modules.yaml
runtime/node_modules/@deepseek-ai/dsh-client-ui-sidebar-terminal/lib/client.terminal.js
runtime/node_modules/@deepseek-ai/dsh-client-ui-sidebar-documentpreview/lib/client.pdf.js
```

profile 的 package.json 已改为 `0.1.4`，但两个 profile lockfile 中仍存在：

```yaml
specifier: file:/plugin/openbkn-dsh-business-context-0.1.4.tgz
version: file:../../../../plugin/openbkn-dsh-business-context-0.1.4.tgz
```

源码原因：

1. `isProbablyText` 从文件名第一个点截取扩展名，漏掉隐藏文件和多点文件名。
2. 路径分割仅识别 `/`，不能可靠处理 Windows 原生路径。
3. file 依赖检查依赖 JSON 的 `"dependencies"` 字样，漏掉 YAML lockfile。
4. 仅删除路径前缀会把原绝对路径变成 `/plugin/...`，并未转换为有效的相对引用。

**建议**：使用可靠的路径/扩展名处理，覆盖隐藏文件、多点文件名、Windows 路径；对 package/lockfile 进行结构化规范化或有依据地移除不应发布的安装元数据。不要全局替换运行时代码中的路径后就视为可移植。

**验收**：增加包含以上文件形态及 YAML file 引用的负例；扫描组装目录和最终压缩包，均不得出现构建根泄漏或不可解析的本地依赖；检查不得依赖构建机仍保有原文件。

### R4 [P1] 将链接复制成文件破坏 `.bin` 入口

**位置**：`runtime/bundle-portability.mjs:43–47`。

`dereferenceSymlinks` 将符号链接替换成目标文件副本，改变了脚本所在位置，进而改变相对模块解析。

本轮使用 Node 实际验证：

```text
node <bundle>/runtime/node_modules/.bin/semver 1.2.3
→ 退出码 1，Cannot find module '../package.json'

node <bundle>/runtime/node_modules/semver/bin/semver.js 1.2.3
→ 退出码 0，输出 1.2.3
```

**建议**：允许安全、包内闭合的相对链接，或为 `.bin` 生成正确的包装器。对外部目录依赖复制后，应保持包布局；“零链接”不是正确性的充分条件。

**验收**：检查真实 `.bin` 入口可执行；增加依赖 `../package.json` 和相对模块的 fixture；在源码树不可见的隔离环境验证。跨平台分别验证可执行权限及包装器行为。

### R5 [P2] Node 守卫与声明不一致，Windows 失败后继续执行

**位置**：`runtime/assemble-compatible-runtime-bundle.mjs:55、70–79`。

- 当前条件放行 Node 23，但声明 `^22.19.0 || >=24.0.0` 不包含 Node 23。
- Windows `.cmd` 在 Node 版本检查失败、bootstrap 失败后没有检查 `errorlevel`，仍继续执行后续命令。

**建议**：使用与声明一致的版本判断；Windows 每个关键步骤失败后立即返回非零退出码。

**验收**：覆盖 Node 20、22.18、22.19、23、24 等边界；用失败 bootstrap 验证不得进入主 CLI。Windows 行为需原生 CI 证据，不能仅靠生成文本检查。

### R6 [P2] 插件发布链仍非冻结安装

**位置**：`.github/workflows/compatible-runtime.yml:43`。

DSH 构建已恢复 frozen，但 bkn-dsh workspace 仍执行：

```sh
pnpm install --no-frozen-lockfile
```

因此整个 Release 依赖闭包仍可能漂移，BLOCKER-3 仅部分闭环。

**建议**：统一工具链和确定性 generator 路径策略，提交相匹配的 lockfile，或采用不改变受控解析结果的明确构建方案，避免以非冻结安装掩盖不一致。

**验收**：从干净 checkout 用 pinned pnpm 安装，不更新 lockfile；重复执行保持受控依赖闭包一致。

### R8 [P2] License 错误分类仍在溯源路由误报

**位置**：`packages/openbkn-business-context/src/platform-reader.ts:118–122`。

已正确避免非 observability 路由误报，但溯源路由仍将 Token 失效引发的 `401 + permission_denied` 映射为企业 License 缺失。开发回应也记录了该现象。

**建议**：不能仅凭路由和共用错误码确定 License 缺失；在无法区分时保留认证/授权不确定性，给出准确提示，或依据明确的 license capability 证据分类。不要以“重开面板会恢复”关闭该缺陷。

**验收**：分别覆盖真实 License 缺失、企业 License 有效但 Token 失效、域授权不足等情形，不应错误提示用户升级 License。
