## 4. 待修复发现

### T1 [P1] 新 portability 测试在 Windows 上存在确定的路径错误

**位置**：

- `tests/bundle-portability.test.mjs:17–24、53、74、97、119、127–132`
- `.github/workflows/compatible-runtime.yml:53`

CI 现在在 Windows job 中执行全部 `tests/*.test.mjs`，其中多个新增 fixture 不是跨平台的：

1. `home` 固定为 `/Users/build-machine`，写入的文本也是该形式；生产函数对 home 调用 `resolve(home)`。Windows 下解析为带盘符和反斜杠的路径，原文本不包含该串，预期的泄漏异常不会产生。
2. `relative(root, path)` 在 Windows 返回 `bin\\tool`，但测试以 `byLink.get('bin/tool')` 和 `.endsWith('.bin/semver')` 查找，结果为 undefined，后续读取 `.kind` 失败。
3. 逃逸链接目标固定为 `/etc/hosts`，Windows 并无该 POSIX 路径保证。`realpathSync` 可能先抛 ENOENT，而测试期待的是 `symlink escapes the bundle`。
4. 清洗测试同样把 POSIX home 文本与 Windows resolve 后路径混用，预期的修改不会发生。

**影响**：即使产品代码能在 Windows 使用，当前测试门禁也会使 win32 job 失败。无需在线 CI 就能从 path.win32 与断言形式确认这些分支差异。

**建议**：fixture 路径用 tmpdir/join 构造；逃逸目标在独立临时目录真实创建；比较路径时使用一致的 join/规范化协议；单独测试 POSIX 和 Windows 序列化路径，而不是拿同一固定文本冒充两者。Windows symlink 权限、类型参数也需实际验证。

**验收**：macOS 与 Windows 原生 `node --test tests/bundle-portability.test.mjs` 均通过，且负例确实由预期的业务异常拒绝，不是意外 ENOENT 或 TypeError。

### T2 [P2] Node 23 仍被两个启动器放行，回应中的修复未落实

**位置**：`runtime/assemble-compatible-runtime-bundle.mjs:55、70`。

实际代码仍是：

```js
if (v[0] < 22 || (v[0] === 22 && v[1] < 19)) { /* reject */ }
```

Node 23 不满足拒绝条件，因此被接受；但声明 `^22.19.0 || >=24.0.0` 不包含 Node 23。开发回应称已改为 `((major===22&&minor>=19)||major>=24)` 且 7/7 通过，与实际提交代码不一致。

Windows `||exit /b 1` 的早退修改确已存在，此项不要混为完全未修改。

**建议**：实际修改两个启动器生成逻辑，并用同一版本契约产生守卫；测试应提取实际生成的脚本，不要只测试另写的正确公式。

**验收**：实际生成的 POSIX/Windows 启动器拒绝 20、22.18、23，接受 22.19、24；Windows 还需原生验证版本失败和 bootstrap 失败都不会进入主 CLI。回应修正为可核实的证据。

### T3 [P2] 指向当前 bundle 内的绝对链接会被保留并通过检查

**位置**：`runtime/bundle-portability.mjs:87–97、151–159`。

修复逻辑只检查 realpath 后的目标是否位于当前 bundle 内：

- `dereferenceSymlinks` 会跳过已经解析到 bundle 内的链接；
- `assertPortableBundle` 也只判断解析后的目标是否在 root 内。

二者没有检查链接本身存储的目标是否是绝对路径。因此：

```text
/tmp/build/bundle/link -> /tmp/build/bundle/target
```

在构建机上会被接受，但移动 bundle 后链接仍指向旧目录。本轮内存探针确认 `assertPortableBundle` 接受此形态。

**范围说明**：本轮当前 tar 的 11 个链接均为相对链接，未在该产物中发现此问题；这是生产规范化及门禁的已证实边界缺口。

**建议**：用 readlink 检查原始目标；对绝对链接，即使目标在当前 root 内，也要转为相对链接或拒绝。相对链接仍需验证最终目标不逃逸。

**验收**：新增“绝对但包内”的负例；规范化后原始 readlink 为相对路径，检查旧形态必须失败；移动后不依赖原 bundle 路径。

### T4 [P2] 包内目录链接被当作文件读取，导致 EISDIR

**位置**：`runtime/bundle-portability.mjs:25–35` 以及调用 walkFiles 的清洗/检查逻辑。

Dirent 对目录 symlink 的 `isDirectory()` 为 false，因此 `walkFiles` 会收集它。后续 `readTextIfTextual` 用 statSync 跟随链接，却未判断 `stat.isFile()`，直接 `readFileSync(path)`。

当一个合法目录链接解析到包内目录时，symlink 合法性检查允许它，但随后文本读取会报 EISDIR。`dereferenceSymlinks` 还显式支持重建 `kind='dir'`，说明并非架构上禁止目录链接。

**影响**：遇到使用包内目录链接的依赖布局，构建清洗或发布扫描会失败。当前样例只充分覆盖了文件型 .bin 链接。

**建议**：区分普通文件、文件链接、目录链接和其他对象；文本读取只处理普通文件目标。目录目标扫描须避免重复遍历和循环，不能以跟随任意链接绕过逃逸检查。

**验收**：包内相对目录链接通过规范化和扫描，目标文件仍被正确检查；外部目录链接、悬空链接、循环链接明确失败，不死循环、不触发非预期 EISDIR。

### T5 [P2] Windows 绝对 file 依赖与 JSON 转义 home 路径仍漏检

**位置**：`runtime/bundle-portability.mjs:124–137、161–170`。

当前 file 检测正则：

```js
/file:(\/|\.\.)/
```

它不匹配 Windows 常见的 `file:C:/build/plugin.tgz`。另外，检查 `text.includes(resolve(home))` 不能匹配 JSON 中转义后的 `C:\\Users\\builder`：原始文本反斜杠转义与实际路径字符串不同。清洗阶段使用直接字符串替换，同样存在差异。

本轮用实际模块逻辑与 path.win32 构造内存输入，包含上述两种问题的 package.json 被接受。

**范围说明**：这是模拟 win32 路径语义的逻辑验证，并非实际 Windows 归档检查；不应把当前 macOS 的零命中外推为 Windows 已安全。

**建议**：对 manifest/lockfile 的依赖字段解析后判断路径/URL；区分盘符绝对路径、UNC、file URL、相对依赖；文本路径清洗和扫描应识别对应格式的转义，而不是只用原始字符串搜索。

**验收**：覆盖 `file:C:/...`、`file:C:\\...`、`file:///C:/...`、UNC、JSON 转义 home 等负例，并在 Windows 真实构建产物上扫描。
