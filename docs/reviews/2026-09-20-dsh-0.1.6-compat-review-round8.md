### 3.2 win32 artifact 归档级核验（实测，本轮新增，开发方未做）

从 run#6 下载 `openbkn-dsh-runtime-win32-x64`：

| 检查 | 结果 |
| --- | --- |

| zip 条目数 | 30 486 |
| zip 内符号链接条目 | 0 —— **正常**：pnpm 在 Windows 用 cmd-shim（`.CMD`/`.ps1`/sh 三件套）而非链接，故 POSIX 的 `.bin` 链接契约在此平台不适用 |

### 3.3 代码改动复核

- `mirrorRelativeFor` 抽取为纯函数、`mirrorsTarget` 改为按 mapping 逐个调用：与原实现语义等价（`rel` 仍取自 normalized key），非回归。新纯单测三条断言（同根命中、同名前缀兄弟树不命中、大小写不同的根仅 win32 互认）正确表达了契约，round7 P0-2 的要求已满足。
- fixture 改为「先拷贝纯文件树，再显式创建指向源树的绝对链接」：不再依赖 `cpSync` 的平台相关链接改写，断言未被弱化（仍要求 `relative-link` 且实际执行）。方向正确。
- 残留（低危，非本轮引入）：`mirrorRelativeFor` 在 win32 返回**小写化**的相对路径，`mirrorsTarget` 据此拼出的链接目标文本也是小写。Windows 路径大小写不敏感故可解析；且如 3.2 所示 win32 实际走 shim，不产生链接，影响面为零。仅记录。

## 4. 本轮发现

### F1（P0）假绿根因只修了一半：两个多命令步骤仍在 pwsh 下

**证据（实测，run#6 windows job 日志逐步骤 `shell:` 行）**：

| 步骤 | shell | 块内命令数 |
| --- | --- | --- |
| Verify compatibility series on a clean pinned tree | **pwsh** | 3（apply / verify / apply --revert） |
| Test plugin and compatibility tooling | bash | 3 ✅ 已修 |
| Build and pack bkn-dsh | **pwsh** | 2（build / pack） |
| Smoke-test the assembled runtime entrypoint | bash | ✅ 新增 |

GHA 的 pwsh 包装以最后一个原生命令的 `LASTEXITCODE` 退出，中途的原生失败不中止脚本——这正是 run#4 假绿被实证的机制。具体后果：

- `apply` 成功 → **`verify` 失败**（补丁漂移、sha256 不符）→ `--revert` 成功 ⇒ 步骤绿。**兼容性校验这一核心发布门禁在 Windows 上形同虚设。**
- `build` 失败 → `pack` 仍可能打出陈旧/残缺 tgz ⇒ 步骤绿，且该 tgz 会被后续 profile/package 步骤装进发布产物。

**修复**：给这两个步骤同样加 `shell: bash` + `set -euo pipefail`（或拆成单命令步骤）。建议顺手在 workflow 里加一行注释说明「多命令 run 块一律 bash」，避免再犯。
**验收**：改后 dispatch 一次两平台全绿；另做一次**负例证明**——临时把 verify 改成必失败（例如传一个不存在的 `--dsh`）确认步骤变红，再改回。

### F2（P1）win32 冒烟绕开了 `bin\dsh.cmd`，而这本可非交互执行

现状：win32 分支直接 `node .../dsh/lib/bin.js --version`，等价于 `dsh.cmd` 里 `:run` 那一行，**跳过了 Node 守卫与 bootstrap 早退**——恰好是 round6 缺口第 2 项要验的东西。回应称「`.cmd` 需 cmd.exe 交互」，该判断不成立：`cmd.exe /c` 是非交互的，Windows runner 上可直接调用；且 3.2 已确认 `--version` 路径经 `goto run` 跳过 bootstrap，不会产生副作用。

**修复**：win32 分支改为 `cmd.exe /c "$bundle\\bin\\dsh.cmd --version"`（bash 里注意反斜杠转义），断言输出含 `0.1.6-alpha.2`。若要一并覆盖守卫的**拒绝**路径，可加一条负例：用 setup-node 装 Node 20 后执行同一命令，断言退出码 1 且 stderr 含 `requires Node`。
**验收**：日志显示命令确实是 `dsh.cmd`；负例步骤退出码 1 且断言命中。

### F3（P2）冒烟步骤硬编码产物目录名，与 manifest 重复

`bundle="release/artifacts/openbkn-dsh-runtime-0.1.6-alpha.2-openbkn.1-${{ matrix.platform }}"` 把 bundle 版本抄进了 workflow。manifest 允许 `0.1.6-alpha.2-openbkn.N`，版本一 bump 该步骤就找不到目录（`set -e` 下会红，属吵闹失败而非静默，但仍是重复真相源）。
**修复**：`node -p "require('./runtime/openbkn-dsh-runtime.manifest.json').bundle.archives.find(a=>a.platform===process.argv[1]).file.replace(/\.(tar\.gz|zip)$/,'')"` 取目录名。
**验收**：`grep -c "openbkn\.1" .github/workflows/compatible-runtime.yml` 为 0（打包步骤的 tgz 文件名另算，见 F3b）。

附带同类项（F3b，P2）：`--plugin release/plugin/openbkn-dsh-business-context-0.1.4.tgz` 在 workflow 中出现两次，插件版本一 bump 就要改三处（package.json、两处 workflow）。建议从 `packages/openbkn-business-context/package.json` 读版本拼名。

### F4（P2）CHANGELOG 新增的 `## 0.1.3 (2026-09-18)` 日期无出处

**实测**：把 0.1.3 写入插件 `package.json` 的提交是 `dbd6410`（2026-09-06）；仓库里**没有任何 2026-09-17 或 2026-09-18 的提交**；也没有 0.1.3 的 tag。归位那四条早期条目的做法正确，日期则是凭空的。
**修复**：改为 `## 0.1.3 (2026-09-06)`，或直接去掉日期（未发布过 tag 的版本不标日期更诚实）。

### F5（P2）移除 darwin-x64 后没有面向用户的说明

CHANGELOG 记了，但 `README.md` / `README.zh.md` 的「Install and start」只说「下载匹配的 Runtime 归档」，没有平台清单。Intel Mac 用户下载页会找不到对应产物且无指引。
**修复**：README 双语各加一句「预构建产物覆盖 darwin-arm64 与 win32-x64；Intel Mac 请走源码构建路径（见 compat README）」。
